## 2. AI 시대에 데이터베이스를 배워야 하는 이유

### 2-1. AI가 SQL을 작성해 준다면 데이터베이스를 배울 필요가 있을까?

필요하다고 생각한다.

AI를 이용하면 SQL을 빠르게 작성할 수 있지만, AI가 작성한 SQL이 실제 데이터 구조와 업무 목적에 맞는지는 사람이 확인해야 한다.

특히 JOIN을 사용할 때 어떤 테이블을 연결해야 하는지, 중복 데이터가 결과에 어떤 영향을 주는지, NULL을 어떻게 처리해야 하는지 등을 이해해야 한다.

따라서 AI는 SQL 작성에 도움을 주는 도구이고, 데이터베이스의 구조와 원리를 이해하는 것은 사람이 해야 할 중요한 역할이라고 생각한다.

### 2-2. AI가 잘못된 SQL을 만들 수 있는 이유

AI가 데이터베이스의 실제 업무 규칙과 데이터의 의미를 항상 정확하게 알고 있는 것은 아니기 때문이다.

예를 들어 JOIN 조건이 잘못되거나, 중복 데이터가 존재하거나, NULL 처리 조건이 필요한 경우 AI가 작성한 SQL이 실행은 되더라도 원하는 결과와 다를 수 있다.

또한 특정 컬럼이 업무상 반드시 유일해야 한다는 규칙도 AI가 자동으로 알 수 있는 것은 아니다.

### 2-3. 데이터베이스 지식이 AI 활용에 필요한 이유

데이터베이스를 이해하면 AI에게 더 정확한 질문을 할 수 있고, AI가 작성한 SQL을 직접 검토할 수 있다.

또한 실행 결과가 예상한 결과와 일치하는지 확인하고, 결과에 이상이 있을 때 원인을 찾을 수 있다.

결국 AI 시대에는 SQL을 직접 작성하는 능력뿐만 아니라 AI의 결과를 검증할 수 있는 데이터베이스 지식이 중요하다고 생각한다.

## 3. JOIN 실습

### 3-1. 데이터 구성

학생 테이블에는 다음과 같은 3명의 학생이 있다.

| student_id | student_name |
|---:|---|
| 1 | A |
| 2 | B |
| 3 | C |

질문 데이터는 다음과 같이 구성했다.

- A: 질문 2개
- B: 질문 1개
- C: 질문 0개

### 3-2. JOIN 후 COUNT 결과

다음 SQL을 실행했다.

```sql
SELECT COUNT(*) AS student_count
FROM ch01_students AS s
INNER JOIN ch01_questions AS q
    ON q.student_id = s.student_id;
```

처음 실행한 결과는 `3`이었다.

하지만 이 결과를 실제 학생 수라고 바로 판단하면 안 된다.

### 3-3. 학생별 질문 수 확인

```sql
SELECT
    s.student_id,
    s.student_name,
    COUNT(q.question_id) AS question_count
FROM ch01_students AS s
INNER JOIN ch01_questions AS q
    ON q.student_id = s.student_id
GROUP BY s.student_id, s.student_name
ORDER BY s.student_id;
```

실행 결과:

| student_id | student_name | question_count |
|---:|---|---:|
| 1 | A | 2 |
| 2 | B | 1 |

학생 C는 질문이 없기 때문에 `INNER JOIN` 결과에서 제외되었다.

### 3-4. 실제 학생 수 확인

```sql
SELECT COUNT(*) AS student_count
FROM ch01_students;
```

실행 결과는 `3`이었다.

따라서 실제 학생 수는 3명이다.

### 3-5. 추가 실험

A에게 질문 하나를 추가했다.

```sql
INSERT INTO ch01_questions
    (question_id, student_id, question_text)
VALUES
    (104, 1, '질문 4');
```

이후 동일한 JOIN COUNT SQL을 다시 실행하자 결과가 `4`로 증가했다.

하지만 실제 학생 수는 여전히 `3`명이다.

### 3-6. 결과 해석

이 실습을 통해 `COUNT(*)`는 항상 학생 수를 의미하는 것이 아니라 JOIN 결과로 만들어진 행의 개수를 센다는 것을 확인했다.

A는 질문이 여러 개이므로 JOIN 결과에서 여러 행으로 나타날 수 있다. 반대로 질문이 없는 C는 `INNER JOIN` 결과에서 제외된다.

따라서 학생 수를 구할 때는 단순히 JOIN 후 `COUNT(*)`를 사용하는 것이 아니라 어떤 데이터를 세고 있는지와 JOIN 방식을 함께 확인해야 한다.

## 4. 중복 데이터 실습

### 4-1. 주문 데이터

다음과 같은 주문 데이터를 만들었다.

| order_code | amount |
|---|---:|
| ORD-001 | 100000 |
| ORD-002 | 200000 |
| ORD-002 | 200000 |

여기서 `order_code`가 하나의 주문을 식별하는 유일한 값이라고 가정했다.

### 4-2. 실행한 SQL

```sql
SELECT SUM(amount) AS total_amount
FROM ch01_orders;
```

실행 결과는 `500000`이었다.

### 4-3. 예상 결과

`order_code`가 유일한 주문 번호라는 업무 규칙을 적용하면 다음과 같이 생각할 수 있다.

- ORD-001: 100000
- ORD-002: 200000

따라서 예상 합계는 `300000`이다.

### 4-4. 결과 해석

SQL 자체는 정상적으로 실행되었다.

`SUM(amount)`는 데이터베이스에 저장되어 있는 세 행의 금액을 모두 더하기 때문에 `500000`이라는 결과가 나온다.

하지만 `ORD-002`가 실수로 중복 입력된 데이터라면 업무적으로 잘못된 결과가 된다.

반대로 같은 주문 코드의 두 행이 실제로 별도의 거래를 의미한다면 `500000`이 맞을 수도 있다.

따라서 SQL 실행 결과만으로 정답을 판단할 수 없고, 데이터가 실제 업무에서 어떤 의미를 가지는지 확인해야 한다.

### 4-5. AI 활용 시 주의점

AI에게 단순히 주문 금액의 합계를 구해 달라고 하면 `SUM(amount)`와 같은 SQL을 작성할 수 있다.

하지만 `order_code`가 유일해야 한다는 업무 규칙까지 AI가 자동으로 알 수 있는 것은 아니다.

따라서 AI가 작성한 SQL을 사용할 때는 데이터의 의미와 업무 규칙을 함께 확인해야 한다.

## 5. 데이터 저장 방식 선택

### 5-1. 개인 독서 기록

**스프레드시트**

책 제목, 저자, 읽은 날짜, 메모 정도의 단순한 데이터를 개인적으로 관리한다면 스프레드시트로 충분하다.

### 5-2. 동아리 행사 목록

**스프레드시트**

행사명, 날짜, 장소, 참석자 등의 목록을 관리하는 정도라면 스프레드시트가 편리하다.

### 5-3. 온라인 강의 서비스

**관계형 DBMS**

온라인 강의 서비스는 회원, 강의, 수강, 결제, 진도, 리뷰 등 여러 데이터가 서로 관계를 가지고 있기 때문에 관계형 DBMS가 적합하다.

## 6. 스터디 모임 관리 서비스 설계

### 6-1. 서비스 선정

**스터디 모임 관리 서비스**

회원들이 스터디를 만들고 참여하며, 모임 일정과 출석, 질문 등을 관리하는 서비스를 가정했다.

### 6-2. 필요한 데이터

- 회원
- 스터디
- 스터디 참여
- 모임
- 모임 출석
- 질문

### 6-3. 데이터 간 관계

#### 회원 ↔ 스터디

한 회원은 여러 스터디에 참여할 수 있고, 하나의 스터디에도 여러 회원이 참여할 수 있다.

따라서 회원과 스터디는 다대다 관계이며 `스터디 참여` 데이터를 통해 연결할 수 있다.

#### 스터디 ↔ 모임

하나의 스터디에는 여러 모임이 있을 수 있다.

따라서 모임이 어느 스터디에 속하는지 확인할 수 있는 관계가 필요하다.

#### 회원 ↔ 모임

한 회원은 여러 모임에 참석할 수 있고, 하나의 모임에도 여러 회원이 참석할 수 있다.

따라서 회원과 모임 사이의 출석 정보를 별도로 관리하는 것이 적절하다.

#### 질문

질문은 작성한 회원과 연결되고, 어떤 스터디에서 발생한 질문인지 확인할 수 있어야 한다.

### 6-4. 설계하면서 확인할 정책

다음과 같은 부분은 실제 서비스의 업무 규칙을 정해야 한다.

1. 한 회원이 동일한 스터디에 중복으로 참여할 수 있는가?
2. 동일 회원의 출석 데이터가 중복으로 입력되면 어떻게 처리할 것인가?
3. 출석 상태나 날짜가 NULL이 될 수 있는가?
4. 탈퇴한 회원의 과거 참여 및 출석 기록을 유지할 것인가?
5. 질문에 스터디 정보를 직접 저장할 것인지, 다른 관계를 통해 확인할 것인가?

데이터베이스 설계에서는 단순히 테이블과 컬럼을 정하는 것뿐만 아니라 이러한 업무 규칙을 함께 결정해야 한다.

## 7. AI를 활용한 설계 검토

### 7-1. AI에게 요청한 내용

스터디 모임 관리 서비스의 데이터 구조를 AI에게 설명하고 데이터 중복 가능성, 테이블 관계, NULL 처리, 회원 탈퇴 후 이력 관리 등에 문제가 없는지 검토하도록 요청했다.

### 7-2. AI 검토 결과와 판단

#### 1. 스터디 참여 중복 가능성

한 회원이 동일한 스터디에 중복으로 참여할 가능성을 확인했다.

**판단: 수정**

동일 회원과 동일 스터디의 중복 참여를 허용하지 않는다면 데이터베이스에서 제한할 필요가 있다고 판단했다.

#### 2. 출석 관계 명확화

회원과 모임 사이의 출석 관계를 별도의 데이터로 명확하게 관리하는 것이 좋다는 의견이었다.

**판단: 수용**

출석 상태와 참석 여부를 관리하려면 별도의 관계 데이터가 필요하다고 판단했다.

#### 3. 질문 데이터의 중복 정보

질문 데이터에 관계 정보를 불필요하게 중복 저장하면 데이터 불일치가 발생할 수 있다는 의견이었다.

**판단: 수정**

관계를 명확하게 설계하고 불필요한 중복 데이터를 줄이는 방향으로 수정할 필요가 있다고 판단했다.

#### 4. 상태 및 날짜의 NULL 정책

상태나 날짜가 NULL이 될 수 있는 조건을 명확하게 정해야 한다는 의견이었다.

**판단: 수용**

NULL 허용 여부는 실제 업무 규칙과 연결되므로 명확한 정책이 필요하다고 판단했다.

#### 5. 탈퇴 회원의 과거 기록

탈퇴한 회원의 과거 참여 및 출석 이력을 어떻게 관리할지 정책을 정해야 한다는 의견이었다.

**판단: 수용**

과거 데이터를 유지해야 한다면 회원의 현재 상태와 과거 활동 이력을 구분해서 관리할 필요가 있다고 판단했다.

### 7-3. AI 검토에 대한 평가

AI를 활용하면 데이터 구조에서 놓칠 수 있는 문제를 빠르게 찾아볼 수 있었다.

특히 중복 가능성, 관계 설정, NULL 처리와 같은 부분을 여러 관점에서 검토하는 데 도움이 되었다.

하지만 AI의 제안을 모두 그대로 적용해서는 안 된다고 생각한다.

예를 들어 탈퇴 회원의 데이터를 삭제할지 보존할지는 기술적인 정답이 아니라 서비스 정책에 따라 결정해야 한다.

따라서 AI는 데이터베이스 설계를 검토하고 아이디어를 얻는 보조 도구로 활용하고, 최종적인 업무 규칙과 데이터 구조는 사람이 판단해야 한다.

## 8. 원천 데이터, 파생 데이터, AI 생성 데이터

### 8-1. 원천 데이터

사용자가 직접 입력하거나 서비스에서 실제로 발생한 데이터이다.

예:

- 회원 정보
- 스터디 정보
- 스터디 참여 정보
- 모임 정보
- 출석 정보
- 질문 내용

### 8-2. 파생 데이터

원천 데이터를 계산하거나 집계해서 만들어지는 데이터이다.

예:

- 스터디별 참여 인원
- 회원별 출석률
- 월별 모임 횟수
- 질문 개수
- 평균 출석률

파생 데이터는 원천 데이터가 변경되면 결과도 달라질 수 있다.

### 8-3. AI 생성 데이터

AI가 기존 데이터를 바탕으로 생성하거나 분석한 결과이다.

예:

- 스터디 추천
- 질문 내용 분류
- 활동 내용 요약
- 회원 활동 패턴 분석
- 학습 방향 추천

AI가 생성한 결과는 실제 원천 데이터와 구분해서 관리할 필요가 있다.

### 8-4. 구분이 중요한 이유

AI가 생성한 결과가 실제 사실이라고 자동으로 보장되는 것은 아니다.

따라서 원천 데이터, 파생 데이터, AI 생성 데이터를 구분하면 데이터의 출처와 성격을 파악하기 쉽고 AI가 만든 결과를 검증하기도 쉬워진다.

## 9. 최종 회고

이번 실습을 통해 AI가 SQL을 빠르게 작성해 줄 수 있더라도 데이터베이스의 기본 개념을 이해하는 것이 중요하다는 것을 알게 되었다.

특히 JOIN 실습에서 `COUNT(*)`의 결과가 항상 실제 학생 수를 의미하는 것이 아니라 JOIN 결과로 만들어진 행의 개수를 의미한다는 것을 직접 확인했다.

학생 A에게 질문이 여러 개 있으면 JOIN 결과의 행 수가 증가하고, 질문이 없는 학생 C는 `INNER JOIN`에서 제외되는 것도 확인했다.

또한 중복 주문 데이터 실습에서는 SQL이 정상적으로 실행되더라도 데이터에 중복이 존재하거나 업무 규칙이 명확하지 않으면 실제 업무에서 원하는 결과와 다른 결과가 나올 수 있다는 것을 알게 되었다.

AI는 SQL 작성과 데이터베이스 설계 아이디어를 빠르게 얻는 데 유용하지만, 데이터의 의미와 업무 규칙까지 자동으로 판단해 주는 것은 아니다.

따라서 AI 시대에는 단순히 SQL을 작성하는 능력뿐만 아니라 **데이터 구조를 이해하고, AI가 만든 SQL과 결과를 검증하며, 실제 업무 규칙에 맞는지 판단하는 능력**이 중요하다고 생각한다.
