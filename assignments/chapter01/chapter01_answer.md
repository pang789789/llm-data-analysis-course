```text
비교하고 데이터의 의미도 확인해야 한다.
```

## 3-3. 잘못된 학생 수 SQL 실행 결과

```sql
SELECT COUNT(*) AS student_count
FROM ch01_students AS s
INNER JOIN ch01_questions AS q
    ON q.student_id = s.student_id;
```

실행 결과:

```text
실행 전 예상: 3명
직접 실행 결과: [실행 후 입력]
```

## 3-4. JOIN 상세 결과 관찰

```text
학생 A가 나타난 행 수: 2
학생 B가 나타난 행 수: 1
학생 C가 나타난 행 수: 0
```

### Q1. 학생 C가 왜 결과에서 사라졌나요?

```text
INNER JOIN은 양쪽 테이블에 JOIN 조건이 맞는 행만 결과에 포함한다.
학생 C는 질문 데이터가 없어서 ch01_questions와 일치하는 행이 없기 때문에
결과에서 제외된다.
```

### Q2. 학생 A가 왜 여러 행으로 나타났나요?

```text
학생 A에게 질문이 2건 있기 때문이다. JOIN은 학생 A 한 명과 질문 두 건을
각각 연결하므로 결과에는 학생 A가 두 행으로 나타난다.
```

### Q3. 위 `COUNT(*)`가 실제로 세고 있었던 것은 무엇인가요?

```text
학생의 수가 아니라 INNER JOIN이 만들어 낸 결과 행의 수를 세고 있었다.
초기 데이터에서는 A 2행 + B 1행 = 3행이다.
```

### Q4. 결과 숫자가 우연히 실제 학생 수와 같아도 바로 믿으면 안 되는 이유는 무엇인가요?

```text
숫자가 같다는 사실만으로 그 숫자가 같은 대상을 의미한다고 볼 수 없기 때문이다.
이 SQL의 3은 학생 3명이 아니라 JOIN 결과 3행이라는 다른 의미의 숫자다.
데이터가 조금만 바뀌어도 두 숫자의 관계가 달라질 수 있다.
```

## 3-5. 질문 한 건을 추가한 뒤 다시 실행

추가한 데이터:

```text
(104, 1, '네 번째 질문')
```

다시 실행한 결과:

```text
AI SQL 결과: 4
실제 학생 수: 3
```

### 결과 해석

```text
데이터가 바뀐 뒤 무엇이 달라졌는지:
학생 A의 질문이 2개에서 3개로 늘어나 JOIN 결과 행도 3(A) + 1(B) = 4행이 되었다.

실제 학생 수는 왜 그대로인지:
새로 추가한 것은 학생이 아니라 학생 A의 질문 한 건이기 때문에 학생 테이블의 행 수는 3명 그대로다.

이 실험을 통해 알게 된 점:
COUNT(*)는 항상 내가 원하는 업무 대상의 개수를 의미하는 것이 아니다.
JOIN 이후 어떤 행이 만들어졌는지 먼저 확인해야 한다.
```

## 3-6. 학생 테이블을 직접 센 결과

```sql
SELECT COUNT(*) AS student_count
FROM ch01_students;
```

결과:

```text
3
```

### 두 SQL의 차이를 내 말로 설명

```text
첫 번째 SQL은 학생과 질문을 INNER JOIN한 뒤 만들어진 결과 행의 수를 세고 있었다.

두 번째 SQL은 학생 테이블에 실제로 저장된 학생 행의 수를 세고 있었다.

따라서 SQL을 검토할 때는 문법보다 먼저 내가 세려고 하는 대상과 실제로 만들어진 행의 의미를 확인해야 한다.
```

# 4. 잘못된 데이터가 결과를 바꾸는 과정

## 4-1. 주문 데이터 확인

```text
ORD-001, 100000
ORD-002, 200000
ORD-002, 200000
```

## 4-2. 실행 전 예상

업무적으로 주문이 `ORD-001`, `ORD-002` 두 건이고 `order_code`가 주문을 고유하게 구분한다고 가정할 경우 예상 합계:

```text
300000 원
```

## 4-3. SQL 합계

```sql
SELECT SUM(amount) AS total_amount
FROM ch01_orders;
```

실제 결과:

```text
500000 원
```

## 4-4. 결과 해석

### `SUM` 문법 자체가 잘못된 것인가요?

```text
아니다. SUM은 저장된 세 행의 amount를 정확하게 더했다.
```

### 결과 차이의 원인은 무엇인가요?

```text
ORD-002가 두 행으로 저장되어 있기 때문이다. order_code가 실제 주문을 고유하게
구분한다는 업무 규칙을 적용한다면 같은 주문이 중복 저장된 것으로 볼 수 있다.
```

### SQL이 정확하게 실행되어도 업무 숫자가 잘못될 수 있는 이유를 설명하세요.

```text
SQL은 데이터베이스에 실제로 저장된 값을 계산할 뿐, 그 데이터가 업무적으로
올바른지까지 자동으로 판단하지 않는다. 따라서 중복·누락·잘못된 업무 규칙이
원본 데이터에 있으면 SQL이 정상 실행되어도 업무 결과는 틀릴 수 있다.
```

## 4-5. AI에게 같은 데이터를 분석시킨 결과

AI가 계산한 합계:

```text
500000 원
```

AI가 중복 가능성을 언급했나요?

```text
예. ORD-002가 두 번 등장하므로 중복 입력 가능성을 확인해야 한다고 판단했다.
```

AI가 `ORD-002` 두 행이 실제 두 주문인지 중복 입력인지 스스로 확정할 수 있나요? 이유도 적으세요.

```text
확정할 수 없다. 데이터에 ORD-002가 두 번 있다는 사실만으로는 실제로 같은 주문이
중복 저장된 것인지, 같은 코드가 서로 다른 주문에 잘못 사용된 것인지, 혹은
애초에 order_code가 고유해야 한다는 규칙이 없는지 알 수 없기 때문이다.
```

추가로 확인해야 할 업무 규칙:

```text
1. order_code가 주문을 반드시 고유하게 구분해야 하는가?
2. 동일한 order_code로 여러 행이 존재할 수 있는가?
3. 중복 주문이 발견되면 분석에서 하나만 인정할 것인지, 모두 인정할 것인지?
```

내가 최종적으로 내린 판단:

```text
현재 데이터만 놓고 SQL SUM 결과는 500000원이지만, order_code가 주문을 고유하게
구분한다는 업무 가정이 맞다면 정상적인 주문 총액은 300000원으로 보는 것이 맞다.
따라서 SQL을 수정하기 전에 데이터 중복과 업무 규칙부터 확인해야 한다.
```

# 5. 파일·스프레드시트·DBMS 선택 연습

## 사례 A. 개인 독서 기록

```text
나의 선택: 스프레드시트

선택 이유: 한 사람이 사용하고 한 달에 5건 정도만 추가되며, 책 제목·날짜·메모 정도의
간단한 정보를 관리하므로 복잡한 관계나 권한 관리가 필요하지 않다.

어떤 조건이 추가되면 다른 방식으로 바꿀 것인지:
여러 사람이 동시에 수정하거나, 독서 기록과 책·회원 등의 관계가 복잡해지거나,
반복적인 집계와 권한 관리가 중요해지면 DBMS를 고려하겠다.
```

## 사례 B. 동아리 행사 신청 명단

```text
나의 선택: 스프레드시트

선택 이유: 운영진 2~3명이 함께 수정하지만 단기간 운영되는 명단이고, 참석 여부와
참석률 계산 정도가 주된 작업이므로 스프레드시트로도 충분하다고 판단했다.

어떤 조건이 추가되면 다른 방식으로 바꿀 것인지:
신청자가 직접 웹에서 계속 신청하거나, 여러 행사를 장기간 관리하거나, 사용자별
권한·변경 이력·복구가 중요해지면 DBMS를 선택하겠다.
```

## 사례 C. 온라인 강의 서비스

```text
나의 선택: 관계형 DBMS

선택 이유: 학생·강사·강의·수강신청 사이에 관계가 있고, 한 학생이 여러 강의를
신청하고 한 강의에도 여러 학생이 신청할 수 있다. 신청 상태와 신청 당시 금액을
관리해야 하며 여러 사용자의 동시 사용, 반복 조회, 권한, 백업·복구도 중요하다.

어떤 조건이 추가되면 다른 방식으로 바꿀 것인지:
서비스가 일회성 소규모 행사로 축소되고 한 사람이 수동 관리하는 단순 목록 수준이
된다면 스프레드시트를 고려할 수 있다.
```

# 6. 나만의 서비스 데이터 구조 초안

## 6-1. 서비스 정의

```text
서비스 이름: 스터디 모임 관리 서비스

이 서비스는
스터디 구성원과 스터디 모임, 참석 기록, 질문을 관리하기 위한 서비스이다.
```

## 6-2. 관리할 데이터 후보

```text
1. 회원
2. 스터디
3. 스터디 참여 정보
4. 모임 일정 및 참석 기록
5. 질문
```

## 6-3. 한 행의 의미

| 데이터 후보 | 한 행의 의미 |
| --- | --- |
| 회원 | 회원 한 명 |
| 스터디 | 스터디 모임 한 개 |
| 질문 | 특정 회원이 특정 스터디에서 작성한 질문 한 건 |

## 6-4. 관계를 자연어로 설명

```text
1. 한 회원은 여러 스터디에 참여할 수 있다.
2. 한 스터디에는 여러 회원이 참여할 수 있다.
3. 하나의 질문은 한 회원이 특정 스터디에서 작성한 하나의 질문 사건을 의미한다.
```

## 6-5. 아직 결정하지 않은 정책

```text
Q1. 탈퇴한 회원의 과거 스터디 참여 기록과 질문을 삭제할 것인가?
Q2. 한 회원이 같은 스터디에 중복 가입하는 것을 허용할 것인가?
Q3. 스터디 모임에 참석하지 않은 회원도 질문을 작성할 수 있게 할 것인가?
```

# 7. AI를 검토자로 활용하기

## 7-1. 내가 AI에게 전달한 핵심 프롬프트

```text
나는 데이터베이스를 처음 배우는 학생이다.
내가 생각한 서비스는 스터디 모임 관리 서비스이고, 목적은 스터디 구성원과
스터디 모임, 참석 기록, 질문을 관리하는 것이다.

관리할 데이터 후보는 회원, 스터디, 스터디 참여 정보, 모임 일정 및 참석 기록, 질문이다.

내가 생각한 관계는 한 회원이 여러 스터디에 참여할 수 있고, 한 스터디에도 여러 회원이
참여할 수 있으며, 하나의 질문은 특정 회원이 특정 스터디에서 작성한 질문 한 건이라는 것이다.

아직 결정하지 못한 정책은 탈퇴 회원 기록 처리, 중복 가입 허용 여부, 미참석 회원의 질문
작성 허용 여부이다.

완성된 SQL을 만들지 말고 내가 놓친 데이터, 서로 다른 의미의 데이터가 섞인 부분,
추가로 확인할 업무 질문, 파일·스프레드시트·관계형 DBMS 중 적합한 방식을 초보자가
이해하기 쉽게 검토해 달라. 확정되지 않은 정책은 임의로 결정하지 말라.
```

## 7-2. AI의 주요 제안과 나의 판단

| AI의 제안 | 수용 / 수정 / 거절 | 나의 판단 근거 |
| --- | --- | --- |
| 회원과 스터디를 별도의 데이터 대상으로 관리한다 | 수용 | 서로 다른 대상을 한 항목에 섞지 않는 것이 의미를 명확하게 하는 데 도움이 된다. |
| 회원과 스터디의 참여 관계를 별도로 관리한다 | 수용 | 한 회원이 여러 스터디에 참여하고 한 스터디에도 여러 회원이 참여하므로 관계 자체를 기록할 필요가 있다. |
| 질문을 회원 정보 안에 직접 저장한다 | 거절 | 질문은 회원의 현재 정보가 아니라 특정 스터디에서 발생한 사건이므로 별도의 데이터 대상으로 보는 편이 의미에 맞다. |
| 참석 기록을 관리한다 | 수용 | 참석 여부는 모임마다 달라질 수 있는 사건 데이터이므로 서비스 목적에 필요한 정보다. |
| 회원 탈퇴 시 모든 기록을 즉시 삭제한다 | 수정 | 실제 업무 정책이 정해지지 않았으므로 삭제 여부를 임의로 결정하면 안 된다. 보존 정책을 먼저 확인해야 한다. |

## 7-3. AI에게 자기 답변을 다시 비판하도록 요청한 결과

첫 번째 답변과 달라진 점:

```text
첫 번째 답변에서는 데이터 항목을 나누는 데 집중했지만, 다시 검토하면서
회원-스터디 참여와 모임-참석 기록처럼 '사건 또는 관계' 자체를 별도로 기록해야
하는 부분을 더 명확하게 확인했다. 또한 탈퇴 회원 기록 보존 같은 정책은 기술적으로
임의 결정할 것이 아니라 실제 운영 규칙을 확인해야 한다는 점을 강조했다.
```

AI가 처음에 임의로 가정했던 내용:

```text
탈퇴 회원을 삭제하거나 비활성화하는 방식, 질문 작성 권한과 같은 운영 정책을
기술적으로 쉽게 결정하려는 부분이 있었다. 하지만 실제 요구사항에 없는 정책은
확정하지 않고 업무 담당자에게 확인해야 한다.
```

추가로 업무 담당자에게 확인해야 한다고 판단한 내용:

```text
탈퇴 회원 데이터의 보존 기간과 삭제 기준
동일 스터디 중복 가입 허용 여부
참석하지 않은 회원의 질문 작성 허용 여부
```

## 7-4. AI 활용에 대한 나의 평가

```text
가장 유용했던 부분:
내가 생각한 데이터 항목에서 놓칠 수 있는 관계와 업무 질문을 찾아주는 데 유용했다.

수정하거나 거절한 부분:
실제 요구사항에 없는 회원 삭제 정책처럼 확정되지 않은 내용을 기술적으로 결정하는
방향은 그대로 받아들이지 않았다.

그렇게 판단한 근거:
데이터베이스 설계에서 중요한 것은 단순히 테이블을 많이 만드는 것이 아니라 실제
업무에서 데이터가 어떤 의미를 가지는지 확인하는 것이기 때문이다.

AI가 없었다면 놓쳤을 가능성이 있는 질문:
탈퇴 회원 기록을 어떻게 보존할지, 중복 가입을 허용할지, 참석하지 않은 회원의
질문을 허용할지 같은 정책 질문을 놓쳤을 가능성이 있다.
```

# 8. 기준 데이터·파생 데이터·AI 생성 결과 구분

| 구분 | 내 서비스의 예 | 판단 이유 |
| --- | --- | --- |
| 기준 데이터 | 회원, 스터디, 참여 및 참석 기록, 질문 | 실제 서비스에서 발생하거나 입력된 원본 기록이기 때문이다. |
| 파생 데이터 | 스터디별 월간 참석률 | 원본 참석 기록을 집계하여 계산한 값이기 때문이다. |
| AI 생성 결과 | AI가 참석률과 질문 내용을 바탕으로 만든 스터디 운영 개선 의견 | 원본 데이터를 지시에 따라 해석·요약하여 만든 결과이기 때문이다. |

### 기준 데이터가 변경되면 파생 데이터는 어떻게 해야 하나요?

```text
파생 데이터를 다시 계산하거나 갱신해야 한다. 특히 원본 기록이 수정되었는데
이전에 계산한 집계값을 그대로 사용하면 현재 원본과 결과가 맞지 않을 수 있다.
```

### AI 결과만 있고 원본 데이터가 없다면 결과를 충분히 검증할 수 있나요?

```text
충분히 검증하기 어렵다. AI가 어떤 원본 데이터를 기준으로 어떤 계산이나 판단을
했는지 확인할 수 없으면 결과가 맞는지 재현하거나 반박하기 어렵다.
```
